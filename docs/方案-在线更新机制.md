# 方案 — EasyRDP 在线更新机制（OTA）

> 需求 R-20261116-005（服务器端与发布流程配套部分）。
> 供客户端（Rust updater）与服务端（官网 PHP / 发布脚本）两侧对齐，本文为协议权威源。

## 1. 总览

```
开发机                                     官网 easyrdp.cn
─────────                                  ───────────────
ota-keygen.ps1（一次性）
  ├─ secrets-vault/ota-keys.enc   （Ed25519 私钥+公钥 + update master，AES-256-CBC/PBKDF2）
  └─ secrets-vault/ota-pub.b64    （公钥，随客户端分发用于验签）
        │ master 人工注入 ──────────────►  api/update/keys.php {"master": "..."}
        │
release.sh 第 9/9 步 → ota-package.ps1
  ├─ 清单签名（Ed25519）──────────►  api/update/latest.json
  └─ AES-256-CTR 加密安装包 ──────►  downloads/EasyRDP-<ver>-portable.exe.enc
                                             ▲
客户端 updater ── 信封请求 ──► api/update/check.php（读 latest.json，信封响应）
```

## 2. 密钥与派生规则

| 密钥 | 存放 | 用途 |
|---|---|---|
| Ed25519 私钥（32B） | `secrets-vault/ota-keys.enc`（加密） | 清单签名（服务器/开发机） |
| Ed25519 公钥（32B） | `secrets-vault/ota-pub.b64`（明文，随客户端分发） | 客户端验签 |
| update master（32B 随机） | `ota-keys.enc` + 官网 `api/update/keys.php` | 信封加解密派生 |

**update 族派生 salt（与客户端约定，勿改；与 feedback 族的 `'enc'/'mac'` 不同，防跨接口密钥复用）：**

```
encKey = HMAC-SHA256(master, "update-enc")   // 32 字节，AES-256-GCM 数据密钥
macKey = HMAC-SHA256(master, "update-mac")   // 32 字节，信封 HMAC 密钥
```

## 3. 信封协议（请求与响应同构）

```
信封 = { "v":1, "alg":"A256GCM-HS256", "ts":<ms>, "nonce":b64, "ct":b64, "tag":b64, "mac":b64 }
ct   = AES-256-GCM(encKey, nonce(12B), 明文)
tag  = GCM 认证标签(16B)
mac  = HMAC-SHA256(macKey, `${ts}.${nonce}.${ct}.${tag}`)   // b64
```

校验顺序（两侧一致）：mac → ts 时效 **±15 分钟** → GCM 解密。
错误响应为明文 JSON `{ok:false,message}`（与 feedback 族一致）。

## 4. 接口 `api/update/check.php`

- 请求：信封包裹任意心跳明文（服务端只验信封不解析内容）。
- 响应明文 = `latest.json` 的 5 字段内容；`latest.json` 缺失/损坏时返回 `{"latestVersion":""}`（客户端视为暂无更新）。
- keys.php：`<?php exit(0); ?>` 退出守卫 + 单行后 JSON（同 feedback 结构），模板见 `api/update/keys.example.php`。

## 5. 清单 `latest.json` 与验签

发布流程（ota-package.ps1）生成，共 5 字段：

```json
{"latestVersion":"0.1.6","file":"EasyRDP-0.1.6-portable.exe","notes":"…","sha256":"…","sig":"…"}
```

**签名覆盖规范 JSON 串**（客户端按同规则重建后验签）：

```
{"latestVersion":"..","file":"..","notes":"..","sha256":".."}
```

固定 4 字段、固定顺序、紧凑无空格、UTF-8（notes 按 JSON 转义）；`sig` = Ed25519 签名 base64。
客户端流程：信封解密 → 取 4 字段重建规范串 → Ed25519 验签（ota-pub.b64 公钥）→
比对本地版本 → 下载 `.enc` → 解密 → 解密结果 SHA256 与 `sha256` 比对 → 校验过才落地执行。

## 6. 加密安装包 `.enc`

- 算法：**AES-256-CTR**（流式，密文与明文等长）。
- 文件密钥（32B）：`HKDF-SHA256(ikm=update_master, salt=0x00×32, info="update-file:"+文件名+明文sha256, L=32)`
- CTR 初始 IV（16B）：`HKDF-SHA256(同 ikm/salt, info="update-file-iv:"+文件名+明文sha256, L=16)`
- 完整性：加密层不加 HMAC；以「解密后 SHA256 == manifest.sha256 + 清单 Ed25519 验签」承担
  真实性/完整性（下载通道本身有 TLS + CDN，清单签名是防篡改根）。

## 7. 密钥存放与安全

- 全部真实密钥只在 `secrets-vault/`（`.gitignore`，禁止入库/外泄/入发布包；release.sh 3.5 步脱敏门禁覆盖 `*.enc`）。
- `ota-keygen.ps1` 幂等：`ota-keys.enc` 已存在默认跳过（`-Force` 才覆盖）。
- 公钥（ota-pub.b64）明文可分发；master 需人工注入官网 `api/update/keys.php`（不自动化，避免密钥经网络明文传输）。

## 8. 发布流程第 9/9 步

`scripts/release.sh` 在第 8 步官网同步成功后：

1. `secrets-vault/ota-keys.enc` 存在 → 调 `ota-package.ps1 -Version <ver>`：
   读 `dist/EasyRDP-<ver>-portable.exe` → SHA256 → 签名生成 `api/update/latest.json` →
   HKDF 派生文件密钥 → AES-256-CTR 生成 `downloads/EasyRDP-<ver>-portable.exe.enc`。
2. scp 上传两者至服务器 `api/update/` 与 `downloads/`。
3. 线上校验：`curl https://easyrdp.cn/api/update/latest.json` 必须 200，否则该步判失败。
4. `ota-keys.enc` 不存在 → 输出 ⚠ 跳过，不失败（向后兼容）。

## 9. 脚本清单

| 文件 | 说明 |
|---|---|
| `scripts/ota-keygen.ps1` | 一次性生成密钥库 + 公钥（本地，不自动执行） |
| `scripts/ota-package.ps1` | 清单签名 + 加密包生成（release.sh 自动调用） |
| `easyrdp-site/api/update/check.php` | 更新检测接口（信封校验/响应） |
| `easyrdp-site/api/update/keys.example.php` | keys.php 模板 |
