## 官网后台/前端 UI 永久规范（项目级，2026-11-22 定版）

- **完整分页六要素强制规范**：凡是官网及管理后台需要分页的列表，分页条必须逐项包含——① 共 X 条 · 第 P/N 页；② « 首页、‹ 上一页、页码（多页带 … 省略折叠）、下一页 ›、末页 »；③ 每页条数下拉（10/20/50，默认值并 localStorage 记忆）。**交付时必须按六要素清单逐项验收，禁止以"对齐/复刻参照物现状"替代规范核对**（教训：2026-11-22 已签发 Token 列表分页首版漏掉每页条数设置与首页/末页，参照物 EasySSH 本身也不完整）。现成参考实现：`easyrdp-site/gw-admin.html` tok-pager（GW-PGFULL-20261122）与 `easyrdp-site/admin.html` gaPagerHtml（GW-PAGE-STD-20261122）。
- **列表卡片折叠默认态规范**：① 官网更新记录——每版本卡片版本号行以下内容默认收起，仅最新版本卡片默认展开，点击标题切换；② 使用反馈——状态「待回复」的卡片默认展开，其余状态默认收起（标题第二行以下折叠），点击标题切换。实现标记 `GW-CARD-FOLD-20261122` / `GW-FBK-FOLD-20261122`（admin.html），可复用 `.upd-fold-body` / `.fb-fold-body` 模式。

## 需求记录来源（分型设计）

所有需求必须先登记入池再开发。来源分型如下，每型写明入口、登记责任人与登记时效：

| 来源分型 | source 取值 | 入口 | 登记责任人 | 登记时效 |
|---|---|---|---|---|
| 官网/应用反馈 | `官网反馈` | 官网反馈渠道 → 反馈内容 AI 复审定时任务判定（real/spam/reject） | 复审定时任务（real 结论自动入池） | 复审判定为 real 后立即登记 |
| 用户会话需求 | `dsh会话需求` | 与用户的 DSH 会话中明确提出 | 当次会话（lead） | 会话内即时登记 |
| 巡检/审计发现 | `巡检审计` | 每日巡检、CI 告警、安全审计 | 巡检会话 | 发现当次登记，须附证据（sourceRef 引用日志/报告） |
| 复审定时任务转化 | `复审转化` | 反馈复审任务把澄清后的反馈转正 | 复审定时任务 | 判定后立即登记 |

流转规则：

- 官网反馈 → 复审定时任务逐条分析 → real 直接入池 / reject 拒绝并留痕 / spam 下架移除；
- 用户会话需求 → 当次会话直接入池（含"已开发未发布"补录）；
- 巡检/审计发现 → 附证据入池，安全类条目需用户审批后才开发；
- 任何来源的条目均走机器池强制登记流程（见需求池文件头），禁止绕过。

## 双轨维护规则（机器池口径）

1. 双轨池，机器池是唯一权威数据源：需求池（本文档同目录 `需求变更记录池.md`）给人看；机器池（`reqpool/requirements-pool.json`）是巡检/发布唯一数据源。巡检只认机器池当前 `status` 字段，两轨必须同步维护；机器池写入只能通过 `scripts/pool-add.ps1`。
2. 禁止手工/内联命令直接改机器池 JSON（中文转义易碎、无校验）。
3. 校验规则：id 格式与唯一、必填字段、status 口径（仅 记录/待开发 参与计数）、`status=记录` 禁带 `releaseVersion`、statusHistory 留痕一致。校验不过不入池。
4. "已开发未发布"补录条目：detail 必须写明【开发状态】与【剩余工作】（"发布时无需再改代码，直接走 版本号+README+构建+push"）。

## 版本号三级递进规则（2026-11-16 用户口径）

以 v.1.2.3 为例：**一级版本号（major，最高级）**满足 10 次二级版本号更新才升级（minor 满 10 → major+1）；**二级版本号（minor，中级）**满足 10 次三级版本号更新才升级（patch 满 10 → minor+1）；**三级版本号（patch）**每升级 10 次推动一次二级升级。另：需求池累计需求每满 10 条 → 本次发布提前升一次二级版本号（里程碑规则，release-check.ps1 自动判定）。规则固化于 `scripts/next-version.ps1` 与 `scripts/release-check.ps1`。

## 发布周期（触发条件 ≥3 条待开发记录 = 规则「池每 3 个可开发的需求推进一次 patch 升级」的自动体现；用户会话指定发布亦可触发）

每日 12:00 定时任务巡检 `requirements-pool.json`：

1. 达阈值 → `scripts/release-check.ps1` 计算下一版本（`next-version.ps1`：patch+1；patch 满 10 升 minor；minor 满 10 升 major）并写 `release-request.json` 标志 + 邮件通知；
2. 发布会话读标志逐条处理 pendingIds：需开发的先开发；"已开发未发布"直接进发布工序；
3. 发布工序（详见 [RELEASE.md](RELEASE.md)）：同步三处版本号（`easyrdp-client/src-tauri/tauri.conf.json` + `easyrdp-client/Cargo.toml` + `easyrdp-gateway/Cargo.toml`）→ README 加 `### v<ver>` 小节 → `bash scripts/release.sh <ver>`（WSL bash；构建→校验→双平台 push→Release→官网徽章同步）→ 机器池条目改「完成发布」+ 写 releaseVersion（statusHistory 追加留痕）→ 删除标志文件 → `scripts/notify-email.ps1` 邮件通知；
4. 发布属敏感操作：需求不明确、需要产品决策或条目带审批门槛（如安全类需用户审批）时，不强行发布，汇报等用户确认；
5. 收尾：需求池对应条目改「已实现/完成发布」+ 实施版本；本手册修订记录追加一行。

## 永久规则

- **对外发布源码包必须脱敏**（加密凭据、服务器 IP/主机名、SSH 密钥、内网拓扑、口令/令牌、个人信息任一命中即禁止发布）；详见 [RELEASE.md](RELEASE.md)。
- 凭据只允许以加密形式存于 `secrets-vault/`；`reqpool/` 目录为机密，禁止外泄、禁止提交入库。
